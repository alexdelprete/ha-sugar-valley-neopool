# Release v2.1.4

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-sugar-valley-neopool/v2.1.4/total?style=for-the-badge)][release]

**Release Date:** 2026-10-03

**Type:** Patch release - Fixes found right after v2.1.3: device firmware and IP now reach the device page, config
registers are read reliably at startup, no more alarming "disabled entity" warnings, and controllers without a
temperature probe get a clean device page. The device page now shows the controller's machine type as the model.
**Requires Home Assistant 2026.8.0 or later.**

> **Upgrading from v2.1.2 or earlier?** v2.1.3 was published the same day and everything in it is included here.
> Home Assistant and HACS only show the notes of the version you install, so v2.1.3's must-knows are summarized in
> [Also included from v2.1.3](#also-included-from-v213) below. Please read that section too.

## What's Changed

### 🔄 Changed

- **The device page shows the machine type as the model; the manufacturer is always Sugar Valley.** The
  controller's `NeoPool.Type` is its machine type (the Sugar Valley product line or OEM variant: Hidrolife,
  Oxilife, Bionet, Generic, Bayrol, Hay, ...), not a manufacturer, but it used to fill the manufacturer field. It
  now fills the model field, with the driver's abbreviated "Hay" shown as "Hayward"; an unassigned type shows as
  "NeoPool Controller". The **System Model** sensor is unchanged and still reports the raw value, so no entity
  state or history changes.

### 🐛 Fixed

- **Device firmware and IP now reach the device page.** At startup the integration asks Tasmota for its firmware
  (`Status 2`) and network details (`Status 5`). Home Assistant's MQTT client sends new subscriptions to the broker
  only after a short cooldown, and Tasmota's reply is not retained, so the reply arrived before the subscription
  and was dropped: the device showed no Tasmota version, and its link pointed at the Tasmota docs instead of the
  device's web UI. The integration now waits until its reply subscriptions are active before asking, gives each
  question its own time budget, and retries in the background once the device reports online.
- **Config registers are read reliably at startup.** The startup read of the config registers (timers, AUX modes,
  heating, pH delay and similar settings) had the same timing problem: the replies to its first reads could be
  lost, leaving those entities unavailable until the next reload. It now waits for its reply subscription first.
- **No more "incorrectly being triggered for updates while it is disabled" warnings.** When the integration
  disabled an entity for hardware the controller does not report, that entity could still try to update once
  while Home Assistant was removing it, logging a warning that called this "a bug in the sugar_valley_neopool
  integration". On v2.1.3 every install saw it once, for the four AUX operating-mode sensors, on the first start
  after upgrading. Disabled entities now never write state.
- **Controllers without a temperature probe get a clean device page.** The Tasmota driver only reports the water
  temperature when the controller has its temperature measurement enabled (the probe is optional). Without it,
  **Water Temperature** and **Smart Antifreeze** used to sit unavailable forever; they are now disabled like any
  other absent hardware, and re-enabled automatically if a probe is reported later.
- **The device is no longer always reported as unavailable in diagnostics.** The integration now tracks the
  device's online/offline status from Tasmota.

## Also included from v2.1.3

Released the same day as this version. The highlights, especially if you are upgrading from v2.1.2 or earlier:

- **Home Assistant 2026.8.0 or later is required** (v2.1.2 needed 2026.3.0). On older versions HACS keeps you on
  v2.1.2; update Home Assistant first.
- **New AUX operating-mode sensors**, `sensor.<prefix>_aux1_operating_mode` through `aux4` (Manual / Timer /
  Countdown), pushed by the Tasmota driver in `Relay.AuxMode`, which **@curzon01** added at our request
  ([arendst/Tasmota #24998][tasmota-pr]). They need the next Tasmota stable after 15.6.0 (or a 15.6.0.1+
  development build); until then they stay **disabled** on the device page, which is expected.
- **AUX mode selects follow the keypad** when your firmware publishes `Relay.AuxMode`.
- **Fixes for two Home Assistant deprecations** that logged warnings with v2.1.2 on Home Assistant 2026.9 and later
  (device lookups) and 2026.10 and later (the `set_timer` service).
- **Example dashboards overhauled**: complete entity coverage, three-column layout, an Alarms row, and conditional
  sections that hide hardware you don't have. HACS does not update the `lovelace/` folder, so re-import the YAML for
  your install type if you want them.
- **Bundled Tasmota firmware updated to v15.6.0** by **@curzon01** ([#24][pr24]).

Full details: [v2.1.3 release notes][v213].

## Upgrade Notes

- **Home Assistant 2026.8.0 or later is required.** Nothing to configure after updating.
- **Expect some entities to be disabled on the device page:** the four AUX operating-mode sensors until your
  Tasmota build publishes `Relay.AuxMode`, and Water Temperature / Smart Antifreeze if your controller has no
  temperature probe. The integration re-enables them automatically when the data appears.
- **The device page now reads "Sugar Valley"** as the manufacturer with your controller's machine type as the
  model. If you referenced the old manufacturer value anywhere (rare), update it.
- The dashboard updates are optional and need a manual re-import, see `lovelace/README.md`.
