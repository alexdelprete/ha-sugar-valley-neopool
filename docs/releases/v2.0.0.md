# Release v2.0.0

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-sugar-valley-neopool/v2.0.0/total?style=for-the-badge)][release]

**Release Date:** 2026-08-19

**Type:** Major release - A large feature release that brings the integration to broad parity with direct-Modbus
NeoPool setups: the pool light becomes a real light, AUX no longer needs the Berry extension, dozens of
controller settings that are not in the SENSOR telemetry become editable entities, and the built-in timers can
be programmed both from a service and from per-timer entities. It also contains **three breaking entity
changes** — please read the upgrade steps below before updating.

## ⚠️ Breaking Changes — Read Before Upgrading

All three changes below **migrate the entities for you** on the first startup after the update: the old
entities are removed from the registry automatically (no lingering "unavailable" entities), the new ones are
created, and the **bundled Lovelace dashboards have already been updated**. What is *not* automatic: any
**automations, scripts, scenes, or custom (non-bundled) dashboards** that referenced the old entities must be
repointed by hand, because Home Assistant cannot rewrite your own references across an entity-domain change.
Also note that historical data / long-term statistics do **not** carry across a domain change (the new
entities start fresh) — this is inherent to changing an entity's domain and cannot be preserved.

### 1. Pool light moved from `switch` to `light`

- Fresh installs: `switch.neopool_light` → `light.neopool_light`
- Migrated installs: `switch.neopool_mqtt_light_switch` → `light.neopool_mqtt_light`

Replace `switch.turn_on` / `switch.turn_off` calls with `light.turn_on` / `light.turn_off`.

### 2. AUX1–4 moved from `switch` to `select` (mode) + `binary_sensor` (state)

- Fresh installs: `switch.neopool_aux<n>` → `select.neopool_aux<n>_mode` **plus** `binary_sensor.neopool_aux<n>`
- Migrated installs: `switch.neopool_mqtt_aux<n>_switch` → `select.neopool_mqtt_aux<n>_mode` **plus**
  `binary_sensor.neopool_mqtt_aux<n>`

AUX is **no longer a plain on/off toggle** — a switch could not represent the controller's three AUX states,
and forcing "off" with a switch would silently override the relay's schedule. It is now a **mode** with
**Auto** (follow the schedule), **On** (force on), and **Off** (force off), plus a read-only state sensor.
Rework automations accordingly: `switch.turn_on` becomes `select.select_option` with `"on"`, and use `"auto"`
to hand control back to the schedule. Read the live relay output from the new `binary_sensor.<name>_aux<n>`.

### 3. "Water Flow" removed; FL1 sensors are now problem-class "Flow Alarm" entities

(Refs [#23][i23], thank you [@deZeus89][deZeus89].) "Water Flow" was an inverted duplicate of the same
`Hydrolysis.FL1` bit, and its name wrongly suggested it tracked pump water flow. Per the Tasmota NeoPool docs
`Hydrolysis.FL1` is the hydrolysis module's flow-detection **alarm** (`1` = flow alarm / no flow), not the
filtration state (that is `switch.<name>_filtration`). `pH.FL1` shares the same polarity, verified empirically
against a live controller. Each FL1 bit now maps to a single problem-class entity (`on` = flow alarm active):

- Fresh installs: `binary_sensor.<device>_water_flow` is removed; the FL1 entities are renamed (entity_ids
  included, so all fresh installs converge on the same IDs): `..._hydrolysis_fl1` → `..._hydrolysis_flow_alarm`
  ("Hydrolysis Flow Alarm") and `..._ph_fl1` → `..._ph_flow_alarm` ("pH Flow Alarm"). Customized entity_ids
  are left untouched.
- Migrated installs: `binary_sensor.neopool_mqtt_hydrolysis_water_flow` is removed; use
  `binary_sensor.neopool_mqtt_hydrolysis_fl1` (YAML-package entity_ids are preserved as before).

**Note the inverted meaning:** the old "Water Flow" entity was `on` when flow was OK; the new flow-alarm
entities are `on` when there is a problem. Update any automations that relied on the old polarity.

## ✨ Added

- **Pool light as a dedicated `light` entity** (`light.<name>_light`). Same relay via `NPLight`, but as a real
  light it now works with light cards, light groups, and "turn on the lights" voice intents. (See breaking
  change #1.)
- **AUX relays without the Tasmota Berry extension.** AUX1–4 are now driven through their controller timer
  block with the built-in `NPWrite`/`NPExec` commands (the timer's function word binds it to the relay, then
  the mode word forces on/off — verified on hardware), exposed as **AUX1–4 mode** selects and read-only
  **AUX1–4** state binary sensors. This removes the integration's only Berry dependency. (See breaking
  change #2.)
- **Configuration controls for settings that are not in the SENSOR telemetry**, read on demand from the
  controller and kept current by command acknowledgments — a lightweight `NPRead`/`NPWrite` layer with **no
  continuous polling**. Each entity self-gates on the relevant module/relay being present:
  - Switches: **UV mode**, **Climate mode**, **Smart antifreeze**.
  - Numbers: **Heating temperature**, **Intelligent minimum filtration time**, **pH pump activation delay**.
  - Hydrolysis cover handling: **Cover reduction** (enable + percentage) and **Temperature shutdown**
    (enable + threshold), which share the controller's bit-packed registers and are written without disturbing
    each other.
- **`sugar_valley_neopool.set_timer` service** to program the controller's built-in timers (filtration 1–3,
  light, AUX1–4), which then run on the controller independent of Home Assistant. Pick a device and timer, then
  set any of: a start+stop time, a repeat period, and a mode (auto/on/off/disabled). **All schedule fields are
  optional and applied granularly** — change only what you want and leave the rest untouched (start and stop
  must be set together). Uses the built-in `NPWrite`/`NPWriteL`/`NPExec` commands and binds each timer's
  function word to its relay (verified on hardware that an unbound timer's schedule is inert).
- **Per-timer entities for the filtration and light schedules.** Each of the three filtration timers and the
  light timer now has a **mode** select (`select.<name>_filtration_timer<n>_mode`,
  `select.<name>_light_timer_mode`; disabled/auto/on/off) plus **start** and **stop** time entities
  (`time.<name>_filtration_timer<n>_start` / `_stop`, and the light equivalents), so a schedule can be viewed
  and edited straight from the UI in addition to the `set_timer` service. Setting a start or stop time
  recomputes the run interval from the other end automatically. These registers are not in the SENSOR
  telemetry, so the entities are read once at startup and kept current by the integration's own writes — they
  do **not** reflect edits made at the controller keypad until Home Assistant restarts, so **timers should be
  managed through the integration**. AUX schedules are not exposed as entities (the AUX mode select already
  covers that register); use `set_timer` for AUX.
- **Per-timer filtration speed for variable-speed pumps.** Three selects
  (`select.<name>_filtration_timer<n>_speed`, Slow/Medium/Fast) let each filtration timer run at its own speed,
  stored in the bit-packed `MBF_PAR_FILTRATION_CONF` register. The integration **auto-detects** a
  variable-speed pump from the controller's reported pump type; a new **Filtration pump type**
  (auto/variable/standard) option can override the detection. The selects stay unavailable on single-speed
  pumps.
- **Automatic time-sync switch** (`switch.<name>_auto_time_sync`): when on, the integration resyncs the
  controller clock (`NPTime`) whenever it drifts more than 60s from Home Assistant. Off by default; state is
  restored across restarts.
- **Reset cell-runtime button** (`button.<name>_reset_cell_runtime`): clears the hydrolysis cell partial/user
  runtime counters. Diagnostic and disabled by default.
